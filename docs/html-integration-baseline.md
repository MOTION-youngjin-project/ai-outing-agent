## 지도·장소 연결 시 보존할 계약

근거: `src/components/NaverMap.tsx`, `src/components/screens/DetailScreen.tsx`, `src/components/screens/ParkingScreen.tsx`, `src/lib/services/places.ts`, `src/lib/clientApi.ts`.

1. 팀의 `placeId`는 DB 장소의 공개 ID(`publicId`)다. 카카오 검색 원본 ID와 다르므로 로컬 작업의 `location.placeId`를 그대로 URL의 `placeId`에 넣지 않는다.
2. 지도에는 실제 검증된 위도·경도만 전달한다. 미확인 좌표를 0이나 지역 중심으로 대체해 장소 마커를 만들지 않는다. 지역 중심은 지도 초기 위치에만 사용한다.
3. 카카오 지도 연결 시 현재 위치·확대/축소·선택 마커·목록·바텀시트 동작을 유지한다. 로컬 SDK의 실패·시간 초과·권한 거부 처리를 이식한다.
4. 장소 검색 REST 키(`KAKAO_API_KEY`)와 지도 JS 키(`NEXT_PUBLIC_KAKAO_JS_KEY`)는 분리한다. 필요한 빈 환경변수에는 `# 여기에 api넣기` 주석을 사용하고 기존 값을 덮어쓰지 않는다. 이번 문서 작업에서는 환경파일을 수정하지 않았다.
5. 네이버 지도 SDK를 바꾸는 것과 별도 네이버 Directions 경로 계산은 다른 작업이다. HTML은 길찾기 제공처로 네이버도 허용하므로 기존 경로 서비스를 지도 교체 때문에 함께 제거하지 않는다.

## 인증·기록 연결 시 주의할 실제 차이

- 팀 `auth()`의 `session.user.id`를 사용자 기준으로 사용한다. DB 쿼리는 팀의 BigInt 타입에 맞추고 외부 응답은 문자열로 직렬화한다.
- 로컬 `User`/`UserSession` 마이그레이션을 그대로 적용하면 기존 팀 계정 구조와 충돌한다. 필요한 추가 테이블·필드만 기존 스키마에 맞춰 별도 마이그레이션으로 설계한다.
- `/api/recent-questions`는 사용자 ID 조건으로 조회하며 `/api/preferences`도 로그인 사용자를 기준으로 동작한다. 코드 존재와 실제 계정으로 저장·조회가 검증된 것은 구분한다.
- 팀 `/api/recommend/[runId]`는 현재 소스상 로그인·소유자 확인 없이 결과를 재조회한다. 개인 추천 이력과 공유 링크의 접근 범위를 구분한 뒤, 후속 기록 통합 시 소유자·만료 확인을 적용할 지점을 검증한다. 이번 작업에서 다른 사람의 기록을 조회하지 않았다.
- 팀 스토어 주석에는 대화 비영속화 설명이 있지만 추천 서비스는 `userQuery`를 기록하는 경로가 있다. 비회원 질문 저장 여부를 주석만으로 단정하지 말고 회원/비회원 실행 검사로 확인해야 한다.
