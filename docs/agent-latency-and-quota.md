# 에이전트 응답시간과 Gemini 쿼터

추천 한 건이 44초 걸리던 것을 9~14초로 줄이면서 실측한 것들. 숫자는 전부 2026-09-12에
LangSmith 트레이스와 API 응답 원문으로 확인했다. 관련 커밋: `perf/first-recommendation-latency`,
`perf/model-chain-by-benchmark`, `fix/agent-unhandled-rejection`.

## 시간이 어디에 있는가

도구 실행(0.4~0.6초)과 서버 후처리(장소 매칭·DB 저장, 0.5초)는 병목이 아니다.
**시간은 모델 왕복과 죽어 있는 외부 API에 있다.** 왕복 1회가 2.5~5초이므로 왕복 수를 줄이는 게
가장 크게 먹힌다.

측정 순서: `pm2 logs`로 에러 종류를 세고 → LangSmith 트레이스로 단계별 소요시간을 보고 →
그래도 설명 안 되는 시간이 남으면 트레이스 **바깥**(모델 폴백 재시도, 서버 후처리)을 본다.
트레이스 조회 방법은 [AGENTS.md](../AGENTS.md)의 "버그를 쫓을 때" 참고.

## 알아낸 지연 원인 (같은 함정이 또 생길 수 있는 것들)

- **라이브러리 내부 재시도.** `@langchain/core`의 AsyncCaller 기본 `maxRetries`는 6이고,
  429 응답의 `retry-after`(40초)를 읽어 실제로 기다린다. 모델 폴백 체인을 직접 갖고 있으면
  이건 순수 중복이다 — `maxRetries: 0`으로 즉시 실패시켜야 한다(27초 → 0.5초).
  **임베딩 클라이언트도 마찬가지다**(`GoogleGenerativeAIEmbeddings`). 도구 하나가 25초를
  먹던 원인이었고, 지금은 `src/lib/embeddings.ts`에서 재시도 1회 + 질의 캐시로 공통 처리한다.
- **응답을 아예 안 주는 모델.** 요청은 받아놓고 아무 이벤트도 안 내는 시도가 있다.
  `stallGuard`가 첫 반응 12초 마감을 걸고, `AbortController`를 `streamEvents`에 넘겨 포기한
  시도를 실제로 끊는다. signal을 안 넘기면 그 실행이 LangSmith에 `pending`으로 영영 남는다.
- **공공데이터 API는 죽을 때 통째로 죽는다.** 문화포털은 8초 타임아웃 x 3회 재시도 구조라
  한 번 막히면 25초를 버렸다. 5초 x 2회로 줄이고 성공은 1시간, **실패는 5분** 캐시한다.
  같은 패턴의 API를 새로 붙일 때도 이 조합(짧은 타임아웃 + 실패 캐시)을 쓸 것.
- **모델에게 이미 아는 값을 묻지 않기.** 날씨·대기질은 서버가 캐시로 갖고 있는데 에이전트가
  도구로 다시 물어서 왕복 2회를 썼다. `describeSituation()`으로 조회해 프롬프트에 넣는다
  (`src/lib/services/recommendations.ts`). 정확도 손실 없이 왕복만 줄어든다.
  **단, 주입한 값이 도구보다 우선한다고 프롬프트에 명시해야 한다** — "비 오는 날" 처럼
  사용자가 날씨를 언급하면 모델이 기존 지시를 따라 같은 값을 도구로 다시 조회했다(실측).

## Gemini 무료 티어 쿼터 (제품 제약이다)

429 응답의 `QuotaFailure` 원문 기준:

- `GenerateRequestsPerMinutePerProjectPerModel-FreeTier` **분당 5회**
- `GenerateRequestsPerDayPerProjectPerModel-FreeTier` **하루 20회**
- **`PerProject`가 핵심**: 같은 Google Cloud 프로젝트에서 새 API 키를 만들어도 쿼터는 공유된다.
  쿼터를 새로 받으려면 **새 프로젝트**를 만들거나 결제를 연결해야 한다.
- 임베딩(`gemini-embedding-001`)은 생성 쿼터와 별개다.
- Pro 계열은 분당 **입력 토큰** 한도에 먼저 걸린다(우리 프롬프트 2.6k 토큰으로도 초과).

**왕복 1회 = 요청 1건**이다. 추천 한 건에 왕복 3~5회이므로 모델 하나당 하루 4~6건이 상한이고,
폴백 체인을 다 합쳐도 하루 20건 안팎이 현실적인 처리량이다. 시연 전에는 쿼터부터 확인할 것.

## 모델 선택

`npx tsx scripts/bench-models.ts`가 같은 질문을 모델별로 돌려 소요시간과 정확도를 잰다.
정확도는 "추천한 장소가 카카오 로컬 검색에 실제로 있는 비율"과 "요청한 구/군에 있는 비율".
`BENCH_MODELS=a,b,c` 로 대상을 지정한다.

**이 벤치 결과를 단독 근거로 쓰지 말 것.** 질문이 3개뿐이라 분산이 크다 — 같은
`gemini-3.5-flash-lite`가 한 실행에서 90%, 다음 실행에서 56%로 나왔다. 순서를 바꿀 거면
질문 수를 늘려 며칠에 걸쳐 재야 한다(하루 쿼터 때문에 한 번에 많이 못 돌린다).

2026-09-12 실측에서 쓸 수 없다고 확인된 모델:

| 모델 | 문제 |
|---|---|
| `gemini-3.6-flash` | 평균 78.7초 — 시도별 타임아웃 25초를 항상 초과. 정확도도 최하위 |
| `gemini-2.5-flash` | 31~52초로 너무 느림 |
| `gemini-2.5-flash-lite` | 구조화 출력(JSON 스키마)을 못 지킴 |
| `gemini-3.1-pro-preview` | 분당 입력토큰 한도 초과로 무료 티어에서 사용 불가 |
| `gemini-3.8-flash`, `gemini-3.7-flash` | 503 "high demand" — 구글 쪽 혼잡, 나중에 재시도할 가치 있음 |
| `gemini-flash-latest` 류 별칭 | 이름에 "gemini-3"이 없어 thought signature 400 에러 |

## 아직 안 풀린 것

추천된 장소의 실재율이 56~90%로 들쭉날쭉하다. 실패 사례는 대개 모델이 "동성로 카페거리 및
실내 체험 공간" 같은 **뭉뚱그린 이름**을 내놓아 검색이 안 되는 경우다. 모델을 바꾸기 전에
"검색 가능한 고유 장소명만 쓰라"는 프롬프트 제약을 먼저 시험해볼 것 — 쿼터도 훨씬 덜 쓴다.
