# 에이전트 응답시간과 Gemini 쿼터

추천 한 건이 44초 걸리던 것을 9~14초로 줄이면서 실측한 것들. 숫자는 전부 2026-09-12에
LangSmith 트레이스와 API 응답 원문으로 확인했다. 관련 커밋: `perf/first-recommendation-latency`,
`perf/model-chain-by-benchmark`, `fix/agent-unhandled-rejection`.

## 시간이 어디에 있는가

도구 실행(0.4~0.6초)과 서버 후처리(장소 매칭·DB 저장, 0.5초)는 병목이 아니다.
**시간은 모델 왕복과 죽어 있는 외부 API에 있다.** 왕복 1회가 2.5~5초이므로 왕복 수를 줄이는 게
가장 크게 먹힌다.

측정 순서: `pm2 logs`로 에러 종류를 세고 → LangSmith 트레이스로 단계별 소요시간을 보고 →
그래도 설명 안 되는 시간이 남으면 트레이스 **바깥**(모델 폴백 재시도, 서버 후처리)을 본다.
트레이스 조회 방법은 [AGENTS.md](../AGENTS.md)의 "버그를 쫓을 때" 참고.

## 알아낸 지연 원인 (같은 함정이 또 생길 수 있는 것들)

- **라이브러리 내부 재시도.** `@langchain/core`의 AsyncCaller 기본 `maxRetries`는 6이고,
  429 응답의 `retry-after`(40초)를 읽어 실제로 기다린다. 모델 폴백 체인을 직접 갖고 있으면
  이건 순수 중복이다 — `maxRetries: 0`으로 즉시 실패시켜야 한다(27초 → 0.5초).
  **임베딩 클라이언트도 마찬가지다**(`GoogleGenerativeAIEmbeddings`). 도구 하나가 25초를
  먹던 원인이었고, 지금은 `src/lib/embeddings.ts`에서 재시도 1회 + 질의 캐시로 공통 처리한다.
- **응답을 아예 안 주는 모델.** 요청은 받아놓고 아무 이벤트도 안 내는 시도가 있다.
  `stallGuard`가 첫 반응 12초 마감을 걸고, `AbortController`를 `streamEvents`에 넘겨 포기한
  시도를 실제로 끊는다. signal을 안 넘기면 그 실행이 LangSmith에 `pending`으로 영영 남는다.
- **공공데이터 API는 죽을 때 통째로 죽는다.** 문화포털은 8초 타임아웃 x 3회 재시도 구조라
  한 번 막히면 25초를 버렸다. 5초 x 2회로 줄이고 성공은 1시간, **실패는 5분** 캐시한다.
  같은 패턴의 API를 새로 붙일 때도 이 조합(짧은 타임아웃 + 실패 캐시)을 쓸 것.
- **모델에게 이미 아는 값을 묻지 않기.** 날씨·대기질은 서버가 캐시로 갖고 있는데 에이전트가
  도구로 다시 물어서 왕복 2회를 썼다. `describeSituation()`으로 조회해 프롬프트에 넣는다
  (`src/lib/services/recommendations.ts`). 정확도 손실 없이 왕복만 줄어든다.
  **단, 주입한 값이 도구보다 우선한다고 프롬프트에 명시해야 한다** — "비 오는 날" 처럼
  사용자가 날씨를 언급하면 모델이 기존 지시를 따라 같은 값을 도구로 다시 조회했다(실측).

## 같은 도구를 반복 호출하다 recursion limit으로 죽는 패턴 (2026-09-13)

벤치에서 "수성구 아이 동반" 케이스가 `Recursion limit of 25`로 실패했다. LangSmith 트레이스
(`01a0965a-2626-7357-a72e-0c4efc18aed4`)를 보니 `search_family_facility_info`를 **11번** 불렀고,
질의를 바꿔도(`수성못 대구 수성구 아이랑`, `국립대구박물관 어린이박물관`, `대구어린이세상` …)
매번 같은 문서 3건(대구미술관, 서울 국립중앙도서관·민속박물관)이 돌아왔다. 모델은 원하는 답이
없으니 계속 재질의했고 왕복 12회를 태우고 요청이 통째로 실패했다 — 하루 쿼터의 절반 이상이다.

**유사도 임계값으로는 못 막는다**(실측): 코퍼스가 9건짜리 데모 요약본이라 점수가 압축돼 있다.

| 질의 | 최고 유사도 |
|---|---|
| 아이랑 갈만한 유모차 이용 가능한 곳(코퍼스가 다루는 주제) | 0.690 |
| 국립대구박물관 어린이박물관(반복 질의, 내용은 대구미술관) | **0.772** |
| 달서구 야외 산책로 주차(코퍼스에 없는 주제) | 0.628 |

관련·무관 질의가 0.58~0.77로 겹치고, 하필 잘못 걸린 질의가 가장 높다. 그래서 임계값 대신
**루프의 판단 지점**을 고쳤다: 도구 결과 끝에 "9건짜리 요약본이라 질의를 바꿔도 같다, 다시
호출하지 말라"를 붙이고(`src/lib/tools/facilityInfo.ts`), 시스템 프롬프트에도 같은 도구를
표현만 바꿔 반복 호출하지 말라는 지시를 넣었다(`src/lib/agent.ts`).

근본적으로는 대구 앱인데 코퍼스 9건 중 8건이 서울·인천 시설이라는 게 문제다 — 데이터를
대구 시설로 교체하면 이 도구가 실제로 쓸모 있어진다(별도 작업).

## Gemini 무료 티어 쿼터 (제품 제약이다)

429 응답의 `QuotaFailure` 원문 기준:

- `GenerateRequestsPerMinutePerProjectPerModel-FreeTier` **분당 5회**
- `GenerateRequestsPerDayPerProjectPerModel-FreeTier` **하루 20회**
- **`PerProject`가 핵심**: 같은 Google Cloud 프로젝트에서 새 API 키를 만들어도 쿼터는 공유된다.
  쿼터를 새로 받으려면 **새 프로젝트**를 만들거나 결제를 연결해야 한다.
- 임베딩(`gemini-embedding-001`)은 생성 쿼터와 별개다.
- Pro 계열은 분당 **입력 토큰** 한도에 먼저 걸린다(우리 프롬프트 2.6k 토큰으로도 초과).

**왕복 1회 = 요청 1건**이다. 추천 한 건에 왕복 3~5회이므로 모델 하나당 하루 4~6건이 상한이고,
폴백 체인을 다 합쳐도 하루 20건 안팎이 현실적인 처리량이다. 시연 전에는 쿼터부터 확인할 것.

## 모델 선택

`npx tsx scripts/bench-models.ts`가 같은 질문을 모델별로 돌려 소요시간과 정확도를 잰다.
정확도는 "추천한 장소가 카카오 로컬 검색에 실제로 있는 비율"과 "요청한 구/군에 있는 비율".
`BENCH_MODELS=a,b,c` 로 대상을 지정한다.

**이 벤치 결과를 단독 근거로 쓰지 말 것.** 질문이 3개뿐이라 분산이 크다 — 같은
`gemini-3.5-flash-lite`가 한 실행에서 90%, 다음 실행에서 56%로 나왔다. 순서를 바꿀 거면
질문 수를 늘려 며칠에 걸쳐 재야 한다(하루 쿼터 때문에 한 번에 많이 못 돌린다).

2026-09-12 실측에서 쓸 수 없다고 확인된 모델:

| 모델 | 문제 |
|---|---|
| `gemini-3.6-flash` | 평균 78.7초 — 시도별 타임아웃 25초를 항상 초과. 정확도도 최하위 |
| `gemini-2.5-flash` | 31~52초로 너무 느림 |
| `gemini-2.5-flash-lite` | 구조화 출력(JSON 스키마)을 못 지킴 |
| `gemini-3.1-pro-preview` | 분당 입력토큰 한도 초과로 무료 티어에서 사용 불가 |
| `gemini-3.8-flash`, `gemini-3.7-flash` | 503 "high demand" — 2026-09-12 재확인, 아래 참고 |
| `gemini-flash-latest` 류 별칭 | 이름에 "gemini-3"이 없어 thought signature 400 에러 |

### 3.8/3.7-flash 재평가 (2026-09-12)

하루 뒤 다시 쟀지만 **여전히 못 쓴다**. 벤치 4케이스씩 = 8회 전부 실패, 에러 원문은 둘 다
`[503 Service Unavailable] This model is currently experiencing high demand.`

단서 하나: `gemini-3.8-flash`는 도구·구조화 출력 없는 짧은 단발 호출은 **성공했다**.
같은 모델이 에이전트 경로(프롬프트 2.6k 토큰 + 도구 6개 + toolStrategy)에서는 5회 연속 503.
혼잡할 때 큰 요청부터 거절되는 것으로 보인다 — "이제 되나" 확인할 땐 반드시 에이전트 경로로
재봐야 하고, 단발 호출이 성공했다는 이유로 폴백 체인에 넣으면 안 된다.
`gemini-3.7-flash`는 단발 호출도 503이다.

## 추천 장소 실재율 (진행 중)

실재율 = 추천한 장소가 카카오 로컬 검색에서 실제로 찾아지는 비율. 측정은 두 가지:

- `npx tsx scripts/place-hit-rate.ts` — **쿼터를 전혀 쓰지 않는다.**
  `agent_runs.recommendation_json.places[].placeId`에 카카오 매칭 성공/실패가 이미 남아 있어서
  과거 실사용 요청을 날짜별로 집계한다(검색 안 된 이름도 그대로 출력). 프로덕션에서도 같은 명령.
  프롬프트·모델을 바꾼 날을 기준으로 표가 before/after로 갈라진다.
- `npx tsx scripts/bench-models.ts` — 모델 호출이 필요해 쿼터를 먹는다(추천 1건 = 왕복 3~5회,
  모델당 하루 20요청). 질문을 8개로 늘렸지만 한 번에 다 돌리면 쿼터를 넘기니
  `BENCH_CASES="실내 데이트,아이 동반"`으로 쪼개 돌린다.

### baseline (2026-09-11 로컬 실사용 10건 / 장소 24개 → 실재율 67%)

검색 안 된 8개의 원인은 두 종류였다:

1. **모델이 내놓은 뭉뚱그린 이름**(5/8) — `동성로 카페거리 및 실내 체험 공간`,
   `수성못 주변 문화 공간`, `의료선교박물관 (동산의료원 내)`,
   `김광석 다시그리기길 (실내 카페/공방)`, `현대백화점 대구점 (더현대 대구)`.
   묶음·범위·괄호 부기가 전부다. → 2026-09-12 시스템 프롬프트와 `PlaceSchema.name` 설명에
   "지도에서 한 건으로 검색되는 고유 장소명만" 제약을 넣었다(`src/lib/agent.ts`).
2. **이름은 맞는데 매칭이 깐깐해서 버린 경우** — `계산성당`은 카카오에 실제로 있다.
   다만 공식 명칭이 `주교좌계산대성당`이고 `계산성당 연도실`도 같이 나와서,
   `pickBestPlaceMatch`(`src/lib/services/matching.ts`)의 "정규화 후 완전일치 1건만" 규칙이
   둘 다 버렸다. **1번을 고친 뒤 브라우저로 재현했더니 이름은 깨끗한데 실재율이 0/2였다** —
   `약령시한의약박물관`(공식명 `대구약령시한의약박물관`), `의료선교박물관`(공식명
   `계명대학교 동산의료원 의료선교박물관`)이 같은 이유로 전부 미매칭. 이쪽이 더 큰 원인이었다.
   → 완전일치가 없으면 **이름을 통째로 품은 후보 중 가장 짧은 것**을 쓰도록 폴백을 넣었다
   (가장 짧은 것 = 군더더기가 가장 적은 후보. `무인민원발급창구 약령시한의약박물관` 같은
   부속 시설을 피한다). 동명이인(완전일치 2건 이상)은 예전처럼 미매칭으로 남긴다.

수정 후 같은 경로로 재현: 위 3개 이름 모두 매칭됨, 브라우저 추천도 1/1 매칭.
표본이 작으니 며칠 쓰면서 `place-hit-rate.ts`로 계속 볼 것.

### 두 수정 적용 후 벤치 (2026-09-13, gemini-3.5-flash-lite 4케이스)

| 케이스 | 결과 |
|---|---|
| 실내 데이트(중구) | 6.9초, 3곳 전부 실재·중구 |
| 아이 동반(수성구) | 실패 — `Recursion limit of 25` |
| 저비용 반나절(중구) | 8.3초, 3곳 전부 실재·중구 |
| 야외 산책(달서구) | 9.0초, 3곳 전부 실재·달서구 |

**실재율 100%(9/9), 지역일치 100%(9/9), 평균 8.1초.** 어제 baseline이 41~67%였다.
벤치는 폴백 없는 단일 모델 실행이라 recursion 실패는 운영 경로에선 다음 모델로 넘어간다
(`isRetryableModelError`가 이미 재시도 대상으로 본다).

### 요청한 구/군을 벗어나는 문제 (2026-09-12)

"중구에서 아이랑 갈만한 곳"에 **수성구** 대구미술관이 나왔다 — 로컬·프로덕션에서 각각 재현,
둘 다 같은 장소에 1곳만. 시스템 프롬프트가 시/도만 다루고 구/군은 아무 말이 없던 게 원인이라
"구/군이 지정되면 그 안의 장소만, 못 채우면 섞지 말고 적게" 지시를 추가했다(`src/lib/agent.ts`).
수정 후 같은 질문: 중구 3곳(달성공원·서문시장·국채보상운동기념공원), 전부 매칭.

**이건 사후 집계로 못 잰다.** `agent_runs.user_query`는 비로그인 요청에서 null이라
(스키마 주석: 추적 안 함) 질문에서 구/군을 뽑는 지표는 로그인 사용자 행에만 동작한다.
실사용 행이 전부 비로그인인 지금은 `bench-models.ts`의 지역일치율(질문을 우리가 아는 경우)이
유일한 측정 수단이다.

### 프로덕션 baseline과 배포 직후 (2026-09-12)

배포 전 프로덕션 누적: **2026-09-11 추천 11건 / 장소 34개 → 실재율 41%**(로컬 67%보다 낮다).
실패 20개의 대부분은 같은 세션에서 반복된 `대구사격장`, `플란트(PLANT)`이고 `이월드 & 83타워`도 있었다.
`플란트(PLANT)`(괄호)와 `이월드 & 83타워`(묶음)는 이번 프롬프트 제약이 겨냥하는 형태이고,
`대구사격장`은 매칭 폴백으로 `대구사격장 매점`에 붙는다.

배포 직후 브라우저로 1건(달서구, 3곳: 두류공원·대구문화예술회관·대구수목원) → **3/3 매칭**.
표본 1건이니 며칠 더 쌓고 판단할 것.
