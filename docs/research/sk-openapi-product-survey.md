# SK Open API(openapi.sk.com) PRODUCTS 메가메뉴 전수 조사 — 기존에 안 쓰던 카테고리 중 쓸 만한 게 있는가

조사일: 2026-09-14
조사 목적: Tmap 보행자 경로안내(SK Open API) 구독을 계기로 콘솔에서 본 PRODUCTS 메가메뉴의 나머지 카테고리(지오비전 퍼즐, TMAP TMS/대중교통, 통신/AI/인증/서비스)를 훑어서, 이 프로젝트(대구 가족 나들이 추천 앱)에 실제로 쓸 데가 있는지 확인. `openapi.sk.com`은 로그인 없이는 대시보드에 못 들어가므로 공개 페이지(상품 소개·요금 계산기)와 연결된 `*.readme.io`/`puzzle.geovision.co.kr` 문서만으로 조사.

**총괄 결론: 지금 당장 도입할 만한 것은 없다.** 가장 기대를 걸었던 "장소 혼잡도"는 대구 커버리지가 확인되지 않을뿐더러, 설계 자체가 백화점·쇼핑몰 같은 건물 단위 상품이라 애초에 "현재 구간"(도보 이동 중) 화면이 필요로 하는 도보 구간 혼잡도와 맞지 않는다. **"유동인구"는 2026-09-14 후속 조사로 확인 완료 — self-serve REST API 자체가 없다(공식 FAQ가 "고객 맞춤형 상품"이라고 명시, 이메일 영업 문의 전용).** 학생 프로젝트가 API 키로 바로 찔러볼 수 있는 상품이 아니므로 재조사 우선순위에서 내린다(아래 1-2절 및 1-2 후속 조사 참고).

## 1. 지오비전 퍼즐(우선순위 최상위)

### 1-1. 장소 혼잡도 — **결론: 대구 커버리지 미확인, 설계상 "현재 구간" 화면과 안 맞음 (도입 보류)**

- 공식 상품 페이지: `openapi.sk.com/products/detail?svcSeq=56`("지오비전 퍼즐 데이터: 장소 혼잡도") — 페이지가 동적 렌더링이라 WebFetch로 본문 상세를 못 읽음(기존 조사 노트와 같은 한계 재확인).
- 대신 자체 소개 사이트 `puzzle.geovision.co.kr/data/쇼핑여가-장소-혼잡도`(WebFetch로 본문 확인)에서:
  - "백화점, 쇼핑센터, 테마파크 등 붐비는 장소"를 대상으로 하며 **"203개(2022.09.26 기준) 장소"**만 등록돼 있다 — 임의 좌표가 아니라 SKT가 사전에 고른 건물 단위 POI 목록.
  - **10분 단위로 갱신되는 실시간 혼잡도**를 제공한다. `congestionLevel` = 추정 방문자 수 ÷ 시설 면적(㎡), 10단계로 분류(레벨5≈100㎡당 2명, 레벨10≈100㎡당 10명 이상) — 언론 보도(`zdnet.co.kr/view/?no=20220705091746`, `hankyung.com/article/202207056452Y`)에서도 같은 방식으로 소개.
  - 예시로 나오는 장소는 전부 서울권이다 — **잠실 롯데월드/롯데백화점 잠실점/에비뉴엘 월드타워점**(뉴스 인용, 10단계 중 8~10단계), 압구정로데오 사례. **대구 소재 매장(대구신세계, 동성로 롯데 등)이 목록에 포함됐다는 근거는 검색 전체에서 단 하나도 나오지 않았다.**
  - 요금(`openapi.sk.com/products/calc?svcSeq=56&menuSeq=263`, 로그인 없이 조회 가능했음): **무료 티어 "장소 목록 10건/월"**, 기본 플랜 **33원/건(일 한도 100건)**, 해커톤 플랜 **11원/건(월 한도 3,000건)**. 즉 상품 자체는 실재하고 요금표까지 공개돼 있으나, 애초에 "장소 목록"이 203개로 고정돼 있어 대구 장소가 그 안에 없으면 돈을 내도 쓸 게 없다.
- **설계상의 근본적 문제**: 이 상품은 "건물(백화점 한 채) 단위" 혼잡도이지, 사람이 걷는 도로/보행로 구간 단위 혼잡도가 아니다. "현재 구간" 화면이 필요로 하는 건 "여기서 다음 안내지점까지 도보 구간이 붐비는가"인데, 이 상품은 설령 대구 매장이 목록에 있었다고 해도 그 매장 건물 내부/앞 혼잡도만 알려줄 뿐 구간 단위 데이터가 아니다. **대구 포함 여부와 별개로, 애초에 이 화면의 요구사항을 충족시키는 상품이 아니다.**

**따라서 기존 조사(`turn-by-turn-navigation-and-congestion-data-sources.md`)의 "혼잡도는 이번 화면에 넣지 않는다"는 결론을 바꿀 근거는 못 찾았다.** 다만 아래 1-2절의 유동인구는 다르다.

### 1-2. 유동인구 — **결론: 이번 조사의 유일한 신규 발견, 미검증이지만 재조사 가치 있음**

우선순위 목록에는 "실시간이면 유용, 행정동 집계면 기존 LGU+ 상품과 같은 이유로 부적합"이라고 돼 있었는데, 조사 결과는 기존에 기각한 LGU+ 유형과 다르다.

- 상품 페이지: `puzzle.geovision.co.kr/data/유동인구`(WebFetch로 본문 확인) — 원문(요약 인용):
  - **"실시간 유동인구 정보를 제공"**, "장소/시간대/연령별로 활동하는 인구를 집계"
  - 공간 해상도: **"50㎡ pCell 단위로 위치를 추정"** — 기지국·통화신호 기반, GPS보다 정밀도가 낮지만 행정동보다는 훨씬 촘촘함(도보 한 구간과 비슷한 스케일).
  - 커버리지: **"전국 250개 시군구에서 제공"** — 대구를 명시적으로 배제하지 않음(전국 시군구 수가 250개 안팎이라 사실상 전국).
- 언론(`한국경제 202207056452Y`) 인용: 퍼즐의 "지도 뷰"는 "가로·세로 각 50m인 정사각형 안에 실시간 유동 인구가 500명 이상이면 보라색, 250~499명이면 주황색, 0~49명이면 흰색" 등으로 표시한다 — 이건 위 유동인구 데이터를 시각화한 것으로 보이며, 격자 단위 실시간 인구 밀도라는 설명과 일치한다.
- **미확정으로 남긴 것(로그인 필요/조사 한계)**:
  - 실제 REST API 엔드포인트·요청 스키마(좌표를 임의로 넣어 조회 가능한지, 아니면 SKT가 미리 정한 격자 ID로만 조회하는지)를 문서에서 못 찾음 — `skopenapi.readme.io` 검색에서도 "유동인구"라는 이름의 레퍼런스 페이지를 못 찾았다(TMAP류처럼 별도 서브도메인에 있을 가능성, 로그인 후 콘솔에서만 보일 가능성 있음).
  - 가격(무료 한도/종량제 단가)도 장소 혼잡도처럼 계산기 페이지가 있는지 못 찾음.
  - **"전국 250개 시군구"라는 커버리지 주장이 실제 대구 좌표에서 0이 아닌 값을 주는지는 확인 못 함** — 기존 조사에서 KOTSA가 "전국 API"라고 홍보했지만 실측하니 대구 데이터가 0건이었던 선례(`kotsa-no-daegu-realtime-data.md`)가 있어, 이 "전국" 표현도 실제 데이터 밀도까지 보장하진 않는다. 특히 통신사 유동인구는 인구밀도가 낮은 지역에서 개인정보 보호를 위해 표본이 적은 격자를 마스킹하는 경우가 흔해서, 대구 도심(동성로 등)은 괜찮아도 외곽 나들이 코스는 데이터가 비어 있을 가능성이 있다.
- **왜 이게 "현재 구간" 화면과 관련 있는가**: 50㎡ 격자 + 실시간이라는 조합은 "도보 구간 하나" 스케일과 얼추 맞아떨어진다. 장소 혼잡도(건물 단위, 203개 한정)보다 이 상품이 오히려 원래 조사 목적(도보 구간 혼잡도)에 더 가깝다 — 다만 이번 조사에서 API 스펙·가격·대구 실측 데이터까지는 확정하지 못했으므로 "쓸 수 있다"가 아니라 "재조사할 가치가 있다" 수준으로만 보고한다.

### 1-2 후속 조사 (2026-09-14, TMAP_APP_KEY 실측 포함) — **결론: self-serve REST API 자체가 없음. 도입 불가로 확정, 재조사 종료**

이전 조사가 미확정으로 남긴 (a) 엔드포인트/스키마, (b) 가격, (c) 대구 실측 데이터를 확인하러 재조사. 결과: **(a)가 "없음"으로 확인되면서 (b)·(c)는 질문 자체가 성립하지 않게 됐다.**

- **공식 FAQ가 직접 답을 줬다.** `puzzle.geovision.co.kr/faq`(WebFetch로 원문 확인, 두 번 재확인):
  - "**유동인구 데이터는 고객 맞춤형 상품으로 판매하고 있습니다.**" — 즉 정해진 REST 엔드포인트로 좌표를 넣어 호출하는 구조가 아니라, 영업 문의 후 계약으로 데이터를 받는 B2B 커스텀 상품.
  - 대조적으로 같은 FAQ는 "**지오비전 퍼즐 API는 모두 SK open API에서 이용하실 수 있습니다**"라고 명시한다 — 지하철 혼잡도·장소 혼잡도·국내 여행·주거생활 등 나머지 퍼즐 상품은 이 "모두"에 포함되어 openapi.sk.com에서 self-serve로 구독 가능하지만, **유동인구는 이 "모두"에서 실질적으로 예외 처리된 상품**이라는 뜻이다.
  - 가격 관련 FAQ 문항도 "정액제 요금은 대량 구매 할인이 가능한 고객에게 별도 계약 후 제공"이라고만 돼 있어, 공개된 무료 티어·종량제 단가가 아예 없다(장소 혼잡도의 `products/calc?svcSeq=56` 같은 요금 계산기 페이지가 유동인구엔 존재하지 않음 — 검색·직접 URL 추정 모두 실패).
  - 문의처: `data-puzzle@sk.com` (영업 문의 전용, API 키 발급 창구가 아님).
- **라이브 실측으로 교차 검증.** 프로젝트의 `TMAP_APP_KEY`(`.env.local`, 이미 Tmap 보행자 경로안내 상품에 구독돼 실서비스 중인 키)로 다음 다섯 가지 그럴듯한 엔드포인트 경로를 실제로 호출해봤다(대구 동성로 좌표 `x=128.5911&y=35.8703` 사용):
  - `https://apis.openapi.sk.com/puzzle/population`
  - `https://apis.openapi.sk.com/puzzle/floating-population`
  - `https://apis.openapi.sk.com/transit/puzzle/population`
  - `https://apis.openapi.sk.com/geovision/population`
  - `https://apis.openapi.sk.com/puzzle/geovision/population`
  - **다섯 개 전부 동일하게 `403 {"category":"gw","code":"MISSING_AUTHENTICATION_TOKEN"}`** 반환.
  - 이 응답이 왜 결정적 증거인지: 같은 키·같은 게이트웨이로 **실제 존재하지만 미구독인** 지하철 혼잡도 엔드포인트(`.../transit/puzzle/subway/congestion/stat/train`)를 호출하면 `403 {"code":"INVALID_API_KEY"}`가 오고, **아예 존재하지 않는 경로**(구독 중인 Tmap 보행자 엔드포인트를 일부러 오타 낸 것)를 호출하면 위와 똑같은 `403 {"code":"MISSING_AUTHENTICATION_TOKEN"}`이 온다. 즉 이 게이트웨이는 "상품 미구독"과 "그런 경로 자체가 없음"을 서로 다른 에러 코드로 구분해서 알려준다 — 다섯 개 추정 경로 전부가 후자였다는 건, 추측한 URL 패턴이 하나도 실제 등록된 라우트가 아니라는 뜻이다(참고로 실제 구독 중인 Tmap 보행자 엔드포인트는 같은 키로 정상 `200`을 반환하는 것도 재확인했다 — 키 자체는 유효함).
  - 물론 이는 "내가 시도한 5가지 경로가 틀렸다"는 증거이지 "유동인구 엔드포인트가 세상에 없다"는 수학적 증명은 아니다. 하지만 FAQ의 명시적 진술과 결합하면, 정식 REST 엔드포인트가 애초에 존재하지 않는다(계약형 데이터 납품 상품이라 API 자체가 없을 가능성이 높다)는 결론에 충분히 힘을 싣는다.
- **커버리지(대구 포함 여부)는 여전히 미확인 — 그러나 더 이상 조사할 방법이 없다.** self-serve API가 없으므로 "좌표를 넣어 0이 아닌 값이 나오는지" 실측 자체가 불가능하다. 확인하려면 `data-puzzle@sk.com`에 영업 문의를 넣고 견적·샘플 데이터를 받아야 하는데, 이는 학생 프로젝트 예산·일정에 맞는 절차가 아니다.
- **왜 이번엔 확정할 수 있었나(vs. 이전 조사의 "미검증"):** 이전 조사는 로그인 장벽 때문에 "문서를 못 찾았다"는 소극적 미확인이었다. 이번엔 (1) FAQ 원문이 명시적으로 "self-serve 아님"이라고 말했고, (2) 실제 유효한 키로 게이트웨이 응답 코드까지 대조해 "그런 라우트가 없다"는 정황증거까지 확보했다 — 두 독립적 증거가 같은 결론을 가리키므로 "재조사 가치 있음"에서 "도입 불가"로 격상.

**조사 한계**: 지오비전 팀에 직접 이메일로 "REST API로 제공 가능한가/가격은"이라고 물어보면 다른 답이 나올 가능성은 이론상 남아있다(대기업 영업 채널이 웹사이트 문구와 다른 상품을 안내하는 경우가 종종 있음). 다만 이건 코드/문서 조사로 닫을 수 있는 질문이 아니라 사람이 영업 이메일을 보내야 하는 절차이므로, 이번 조사 범위 밖으로 남겨둔다.

### 1-3. 음식점 — **결론: 평점/리뷰 아님, 통화량 기반 순위(다른 종류의 데이터)**

- WebSearch로 얻은 공식 소개 요약(원문 인용): **"리뷰나 평점이 아닌 통화량 기반의 신뢰할 수 있는 맛집 순위 데이터를 제공"**.
- 즉 `DetailScreen.tsx`가 원칙적으로 비워두고 있는 "평점(rating)·리뷰수(reviewCount)·리뷰 텍스트"에 해당하는 데이터가 **아니다** — 전화 통화량으로 추정한 "인기 순위"라는 전혀 다른 지표다. 카카오/네이버/TourAPI에 없는 데이터인 건 맞지만, 프로젝트가 찾던 "실제 평점/리뷰"의 대체재는 아니다.
- 개별 상품 상세 페이지(엔드포인트·스키마·가격·대구 커버리지)는 URL을 찾지 못해 확인 못함 — 검색 스니펫 수준의 근거만 있음(미검증 표시).
- 상권분석(사업자용) 성격이 강해 보이고, 소비자 앱에 "이 식당이 인기 순위 3위"처럼 노출하려면 그 자체로 별도 검증(정말 대구 식당 포함되는지, 순위 산출 방식이 신뢰할만한지)이 필요하다 — 지금 단계에서 쫓아갈 우선순위는 아니라고 판단.

### 1-4. 국내 여행 — **결론: 관광 마케팅용 집계 통계, 이번 화면들과 무관**

- `puzzle.geovision.co.kr/data/국내-여행`(WebFetch 확인): **행정구역(시군구/동리) 단위** 데이터이고 **"전국 250개 지역 중 123개"**만 다룬다. 대구 포함 여부는 페이지에 명시 안 됨.
- 실시간이 아니라 주/월 단위 집계(방문자 수, 체류시간, 인기 방문지 랭킹)로 보임 — "현재 구간"류 실시간 화면과는 애초에 무관하고, 코스 추천에 "이 지역이 요즘 인기"류 배지를 붙이는 정도로나 쓸 데이터. 지금 로드맵에 그런 기능이 없어 더 파고들지 않음.

### 1-5. 주거생활 / 학원 — **결론: 상권분석/부동산 분석 상품, 이 앱과 무관 (빠르게 스킵)**

- `about` 페이지 요약: **주거생활 = "지역·아파트의 부동산 문의 증감 분석"**, **학원 = "학원가 분석 결과(인기 학원, 이동 흐름)"**. 둘 다 B2B 상권/부동산 분석용이지 소비자에게 보여줄 장소 속성(평점·분위기·혼잡도) 데이터가 아니다. 지시받은 대로 깊이 파지 않고 스킵.

### 1-6. 지하철 혼잡도 — **결론: 수도권 전용, 대구는 원천적으로 대상이 아님 (확인됨)**

- 실제 API 문서(`transit.tmapmobility.com/docs/puzzle/train`, `/docs/puzzle/car`, WebFetch로 본문 확인):
  - 엔드포인트: `GET https://apis.openapi.sk.com/transit/puzzle/subway/congestion/stat/train?routeNm={노선명}&stationNm={역명칭}` (칸별은 `.../stat/car`)
  - 파라미터: `routeNm`(노선명, 예 "1호선"), `stationNm`(역명), 선택 `dow`(요일)/`hh`(시간대 05~23)
  - 응답: 열차 혼잡도(%, 예 `congestionTrain: 36`), 칸별 혼잡도는 "한 칸 160명 = 100%" 환산.
- `puzzle.geovision.co.kr/data/지하철-혼잡도`(WebFetch 확인): **"수도권 1~9호선, 신분당선, 공항철도 모든 역사"** 대상이라고 명시. 실시간 서비스는 그중에서도 **"현재 수도권 2호선, 3호선에 대해서만"** 제공된다고 추가로 제한. **대구 1~3호선은 커버리지 목록에 아예 없다** — 지시받은 대로 깊이 안 파고 여기서 종료.

## 2. TMAP TMS / TMAP 대중교통 — 간단 확인

### 2-1. TMAP TMS — **결론: 무관 (물류 배차 최적화, 소비자 앱 기능 아님)**

- `skopenapi.readme.io/reference/tms` 요약: 택배/방문 일정 등 **물류 배차 계획을 최적화**하는 API(Simulated Annealing 기반, 냉장/냉동/상온 차량 배정, 왕복 경로 비대칭 반영). 나들이 코스 추천 앱과 접점이 없어 더 조사하지 않음.

### 2-2. TMAP 대중교통 — **결론: 이론상 가능하지만, 지금 쓰는 Transitous를 대체할 근거 부족 (보류)**

- 현재 코드(`src/lib/services/transit.ts`)는 **Transitous**(오픈소스 MOTIS 엔진, 무료, 인증키 불필요)를 쓰고 있고, 2026-09-09 실측으로 대구/서울/부산/광주 버스·지하철·기차 응답을 이미 확인해 뒀다(`other-team-api-stack-evaluation.md`).
- TMAP 대중교통(`transit.tmapmobility.com`, `openapi.sk.com/products/detail?svcSeq=59`) 소개 요약: 전국 GTFS 기반 대중교통 경로탐색 + 도보 구간 결합, "실시간/예측 교통정보를 반영"한다고 홍보 — Transitous가 정적 GTFS 위주인 것과 달리 실시간 지연 반영 여지가 있다는 점은 차별점 후보.
- 다만 **요금제(무료 티어 유무)와 커버리지 세부사항을 상품 상세 페이지에서 확인하지 못했다**(WebFetch로 본문을 못 읽음, "API 사용 요금" 섹션이 별도 클릭이 필요해 보임 — 로그인 필요 가능성). 이미 무료로 작동 중인 대체재가 있는 상황에서, 확인 안 된 유료 상품으로 갈아탈 이유가 지금은 없다.

## 권장사항

1. **당장 아무것도 새로 붙이지 않는다.** 이번 조사로 새로 도입을 정당화할 만한 상품은 없었다.
2. **"현재 구간" 화면의 혼잡도 공란 결정은 유지한다.** "장소 혼잡도"는 대구 포함 여부도 불명확하고, 설계(건물 단위 203곳)가 애초에 도보 구간 혼잡도와 안 맞아 이 화면에는 못 쓴다.
3. ~~유동인구는 별도로, 나중에 재조사할 가치가 있다~~ → **2026-09-14 후속 조사로 종결.** self-serve REST API가 없는 계약형 커스텀 상품(공식 FAQ 확인 + `TMAP_APP_KEY` 실측으로 교차검증). 재조사 우선순위에서 제외한다. 정말 필요해지면 코드/문서 조사가 아니라 `data-puzzle@sk.com`에 영업 문의를 넣는 사람의 절차이므로, 그건 "조사"가 아니라 "영업 컨택 여부를 팀이 결정할 문제"로 넘긴다.
4. **음식점(통화량 기반 순위)도 평점/리뷰 정책과는 무관하다는 점을 팀에 공유만 해둔다** — "리뷰가 없으니 어떻게든 대체 데이터를 넣자"는 압력이 나올 때, 이게 답이 아니라는 걸 미리 알아두면 좋다.
5. 지하철 혼잡도(수도권 전용)와 TMAP TMS(물류용)는 이 프로젝트에 원천적으로 안 맞으니 향후 재검토 우선순위에서 제외해도 된다.

## 조사 한계 (투명성 고지)

- `openapi.sk.com`의 상품 상세 페이지(`/products/detail?svcSeq=...`) 다수가 동적 렌더링이라 WebFetch로 본문을 거의 못 읽었다 — 요금 계산기 페이지(`/products/calc?...`)는 예외적으로 읽혔다(장소 혼잡도 요금은 이 경로로 확인).
- 로그인이 막혀 있어 콘솔 내부의 실제 API 레퍼런스(특히 "유동인구", "음식점" 상품의 정식 엔드포인트·스키마)는 전혀 확인하지 못했다 — 이번 조사는 `puzzle.geovision.co.kr`(마케팅용 소개 사이트)과 언론 보도, 그리고 이미 공개된 `transit.tmapmobility.com/docs/puzzle/*`(지하철 혼잡도만 해당) 레퍼런스에 의존했다.
- (2026-09-14 갱신) "유동인구"가 실제 대구 좌표에서 0이 아닌 값을 주는지는 여전히 실측하지 못했다 — 다만 이제는 "문서를 못 찾아서"가 아니라 "애초에 좌표를 넣어 호출할 self-serve 엔드포인트가 없어서"다(1-2 후속 조사 참고). 대구 커버리지 자체를 확인할 방법이 이메일 영업 문의 외엔 없다는 게 이번 조사의 최종 결론이다.
- "장소 혼잡도"의 203개 등록 장소 목록 자체(어떤 장소가 포함되는지 전체 리스트)는 어디서도 원문으로 확인하지 못했다 — 언론에 인용된 예시(잠실, 압구정로데오)가 전부 서울이라는 정황 증거만으로 "대구 미포함 가능성이 높다"고 판단했을 뿐, "대구가 0곳이다"라고 확정한 것은 아니다.
- 음식점/국내여행 상품의 정확한 API 엔드포인트, 요청/응답 스키마, 가격은 전혀 확인하지 못했다(WebSearch 스니펫 수준) — 실제로 검토한다면 로그인 후 콘솔에서 재확인 필요.
- TMAP 대중교통의 요금제(무료 티어 존재 여부)를 확인하지 못해, "지금 쓰는 Transitous보다 나은가"라는 질문에 결론을 내리지 못했다 — 보류일 뿐 "무관"으로 확정한 건 아니다.
