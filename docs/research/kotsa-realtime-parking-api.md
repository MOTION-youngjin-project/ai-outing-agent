# KOTSA 주차정보 API 실시간정보(PrkRealtimeInfo) 조사 — 폐기 결론

조사일: 2026-09-10 ~ 2026-09-11
조사 목적: 한국교통안전공단_주차정보 제공 API(https://www.data.go.kr/data/15099883/openapi.do)로
대구 주차장의 실시간 잔여면수를 채울 수 있는지. 전국 확장 시 실시간 주차 소스로 쓸 값어치가 있는지.

**결론: 실시간정보(`PrkRealtimeInfo`) 엔드포인트는 쓸 수 없다.** 데이터가 사실상 비어 있다.
시설정보(`PrkSttusInfo`, 위치·이름)만 정상이다. 실시간이 필요하면 다른 소스를 찾아야 한다.
대구는 어차피 `src/lib/tools/parking.ts`(대구광역시 통합주차정보시스템, pis.daegu.go.kr)가
이미 실시간 소스라 이 API가 필수도 아니었다.

## 실측 근거

- **대구**: 시설정보에서 대구 72,557건은 정상적으로 찾힌다. 그런데 실시간정보 78.7만 행을
  전부 훑어도 대구 소속 `prk_center_id`가 **단 하나도 없다**. 좌표 최근접 매칭(50m)으로 기존
  `parking_lots` 831건을 연결했는데도 실시간 값이 붙는 건 **0건**.
- **서울로 재검증**: "대구만 빠진 건가" 싶어 서울 시설 id 10개로 같은 방식 재검증.
  78.7만 행 전체(79페이지 100% 완주, 스킵 없음) 스캔에도 정확 매칭 **0건**, 느슨한 지역대
  프리픽스 매칭도 19건(0.003%, 페이지 1에만 몰림 — 노이즈 수준).
- 필드명·매칭 로직 문제가 아니다(둘 다 재확인). 엔드포인트 자체가 전반적으로 비어 있다.

## 다시 건드릴 때 알아둘 것 (시설정보만 쓸 이유가 생긴다면)

- **지역/ID 필터 파라미터가 없다**(2026-09-10 실측). 전국을 페이지로 다 훑어야 한다 —
  시설정보 176만 행, 실시간정보 78.7만 행.
- `numOfRows=10000`이 최대이자 가장 안정적. 1000/5000은 오히려 `SERVICETIMEOUT_ERROR`가 잦다.
- 페이지별 랜덤 SERVICETIMEOUT은 재시도 3회(백오프 1.5초×시도)로 대부분 극복된다.
  177+79페이지 완주에 4시간이 안 걸렸다(2026-09-11 실측).
- **id 체계가 우리 것과 다르다.** KOTSA `prk_center_id`(`00000-19199-00003-00-1`)와 기존
  `ParkingLot.sourceParkingKey`(전국주차장정보 표준데이터, `117-2-000013`)는 직접 join이 안 된다.
  좌표 최근접(50m 임계) 매칭으로 붙여야 한다. 주차장끼리는 보통 50m 이상 떨어져 있어 오매칭은 적었다.
- 전체 스캔이 40분 이상 걸리고 원인불명으로 멈춘 적이 있으니(2026-09-10), 단계별 체크포인트를
  파일로 남기고 재실행 시 건너뛰게 하는 게 좋다.

이 조사에 쓴 일회성 스크립트(`prisma/syncKotsaDaeguParking.ts`)는 결론이 "쓰지 말 것"이라
레포에 남기지 않았다 — 필요하면 위 내용으로 다시 짜는 편이 빠르다.
