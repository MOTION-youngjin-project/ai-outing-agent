# 장소 대표사진 품질 필터링 방법 조사

조사일: 2026-09-08
조사 목적: TourAPI `firstimage`(대표이미지)가 실제로는 부적절한 사진(대구미술관 사례: 장애인 화장실 안내 사진)으로 나오는 걸 자동으로 걸러내거나 더 나은 사진을 고를 방법이 있는지 확인. `place-images-data-sources.md`의 후속 조사.

---

## 1. TourAPI 자체 메타데이터로 구분 가능한지

**결론: 확인 불가.** 아래 경로를 전부 시도했으나 1차 출처로 검증하지 못함.

- `cpyrhtDivCd`(저작권 구분 코드)의 Type1/Type2/Type3 값이 각각 무엇을 의미하는지: 공식 상세페이지(data.go.kr)는 필드 설명이 실제 응답 예시 없이 요약만 있고, 오퍼레이션별 상세 명세는 다운로드 전용 zip 매뉴얼(`개방데이터_활용매뉴얼(국문).zip`)과 JS 렌더링 SPA(`api.visitkorea.or.kr`)에만 있어 이번 조사 도구(WebFetch)로는 열람 불가. Google/Bing/DuckDuckGo 검색도 시도했으나 이 필드를 설명하는 결과를 찾지 못함(검색 결과 자체가 캡차/차단되거나 무관한 결과만 나옴). 기존 프로젝트 문서가 인용한 velog 글도 `cpyrhtDivCd: "Type3"` 값만 예시로 보여줄 뿐 의미는 설명하지 않음.
- `detailCommon2`(공통정보조회)에 `firstimage`가 포함되는지, `searchKeyword2`/`detailImage2`의 `firstimage`와 같은 소스인지: **확인 불가**(같은 이유로 상세 응답 명세 열람 실패). TourAPI 문서 구조상 "대표이미지" 자체가 콘텐츠 하나에 연결된 단일 값으로 관리되는 것으로 보이나(추정, 미검증), 오퍼레이션마다 별도로 큐레이션된다는 근거는 찾지 못함.
- `imgname`/`serialnum`에 "대표"/"편의시설" 등을 구분하는 명명 규칙이 있는지: 확보한 실제 예시 두 건(`대구미술관_6`, `수원화성의 비밀 2020(2)`)을 보면 둘 다 사람이 자유롭게 붙인 제목/순번일 뿐, 사진 종류를 나타내는 통제된 값이 아님. **패턴 없음.**
- 커뮤니티에 "대표이미지가 이상하다(화장실 사진 등)"는 동일 불만 사례: 이번 조사에서 접근 가능한 소스로는 **찾지 못함**(검색엔진이 대부분 차단되어 있어 "없다"고 단정할 수는 없고, "이번 조사로는 못 찾았다"는 수준).

**즉, TourAPI가 제공하는 메타데이터만으로 "이 사진은 편의시설 안내판이다"를 걸러낼 근거 있는 방법은 없다.**

## 2. Gemini Vision으로 후보 사진 중 고르기 — 기술적으로는 되지만 이 프로젝트엔 안 맞음

공식 문서(ai.google.dev/gemini-api/docs/image-understanding, 1차 출처 확인)로 확인한 사실:

| 항목 | 확인 내용 |
|---|---|
| 이미지 입력 방식 | **URL을 직접 줄 수 있음**("Passing image using URL: Ideal for publicly accessible images") — TourAPI 이미지 URL이 공개 URL이라 바로 넣을 수 있음. Base64/Files API도 대안으로 지원. |
| 지원 모델 | 문서상 모든 Gemini 모델이 멀티모달("All Gemini model versions are multimodal") — 이 프로젝트가 이미 쓰는 gemini-3.x 계열도 포함. |
| 다중 이미지 | 한 요청에 최대 3,600개 이미지 파일까지 지원 — 갤러리 5~15장 정도는 문제없이 한 번에 넣을 수 있음. |
| 토큰 비용 | 작은 이미지(384px 이하) 기준 **장당 258토큰**, 큰 이미지는 768×768 타일 단위로 타일당 258토큰. 15장 넣어도 수천 토큰 수준 — 이 프로젝트 시스템 프롬프트(수백 단어) 대비 크게 부담스러운 수준은 아님. |

**그런데 진짜 문제는 토큰이 아니라 "요청 횟수"다.** ai.google.dev/gemini-api/docs/rate-limits(1차 출처)에서 모달리티별로 RPD(하루 요청 한도)가 따로 계산되는지는 문서에 명시돼 있지 않았지만, 이 세션에서 직접 실측한 429 에러 메시지 자체가 `generativelanguage.googleapis.com/generate_content_free_tier_requests`라는 지표명으로 **"콘텐츠 생성 요청" 자체를 세고 있고, gemini-3.6-flash는 하루 20건뿐**이라는 걸 이미 확인했다(`docs/research/ai-outing-agent-recommend-latency-root-cause.md` 관련 세션 실측). 이미지를 넣든 텍스트만 넣든 이 요청 카운트에서 빠질 근거가 없다 — 즉 **사진 하나 고르는 데 Gemini를 한 번 더 부르면, 이미 하루 20번밖에 안 되는 추천 기능용 쿼터를 그대로 깎아먹는다.** 이 프로젝트의 핵심 기능(나들이 추천)이 오늘도 쿼터 소진으로 여러 번 실패했던 걸 감안하면, 부가 기능(사진 고르기)에 같은 자원을 쓰는 건 우선순위가 뒤바뀐 선택이다.

## 3. 그 외 가벼운 대안

- **이미지 크기/종횡비/파일명 휴리스틱으로 편의시설 사진 필터링**: 검증 가능한 근거 없음. 확보한 예시 사진 2장(화장실 안내 사진 vs 정상 입구 사진)만으로 일반화된 패턴(해상도, 종횡비 등)을 판단하는 것은 표본이 너무 적어 추측에 불과함 — **검증 불가로 남김.**
- **무료 이미지 분류/태깅 API**: 이번 조사에서 별도로 찾지 못함(범위상 깊이 조사하지 않음 — Gemini Vision 결론이 이미 "기술적으로 되지만 비용 문제"로 정리되면서, 다른 유료/무료 이미지 분류 API를 추가로 들이는 것 자체가 이 프로젝트 규모에 안 맞다고 판단해 조사를 확장하지 않음).

## 권장 사항

**아무것도 하지 않는 게 낫다.** 이 프로젝트(무료 Gemini 쿼터도 빠듯한 학생 프로젝트) 규모에서:

1. TourAPI 메타데이터로 자동 필터링할 근거 있는 방법이 없다(1번 조사 결과).
2. Gemini Vision은 기술적으로는 쉽지만, 이미 하루 20건짜리 쿼터를 부가 기능에 쓰는 건 손해다 — 사진 하나 잘못 나오는 것보다 추천 기능 자체가 쿼터 소진으로 안 되는 게 훨씬 큰 문제인 상황에서, 후자를 악화시키면서까지 전자를 고칠 이유가 없다.
3. 휴리스틱은 근거가 없어 시도해도 신뢰할 수 없다.

**굳이 뭔가 하고 싶다면**(권장하지는 않음): 자동화 대신, 눈에 자주 띄는 소수의 "대표 장소"(예: 홈 화면에 자주 노출되는 몇 곳)만 사람이 직접 확인해서 `PlaceImage.isPrimary`를 수동으로 다른 갤러리 사진으로 바꿔주는 정도가 이 프로젝트 규모에 맞는 유일한 실용적 절충안이다 — 코드 추가 없이 데이터만 수정하면 됨. 자동 분류 엔진을 만드는 건 이 문제의 크기에 비해 과한 엔지니어링이다.

## 조사 한계 (투명성 고지)

- `cpyrhtDivCd`와 `detailCommon2`의 `firstimage` 관련 질문은 공식 문서(zip 매뉴얼, JS SPA Swagger)에 막혀 **1차 출처로 확정하지 못했다** — 이 문서의 가장 큰 공백. 정말 필요하면 브라우저로 `api.visitkorea.or.kr`를 직접 열어(로그인/키 발급 후) Swagger UI에서 확인해야 한다.
- "커뮤니티에 같은 불만이 없다"는 것은 검색엔진 접근이 막혀서 못 찾은 것이지, 실제로 없다는 뜻은 아니다.
- Gemini API의 RPD가 모달리티(텍스트 vs 이미지 포함)별로 진짜 분리되는지는 공식 rate-limits 문서에 명시적 문장이 없어서, 이 세션에서 실측한 에러 메시지(요청 자체를 세는 지표명)로 추론한 것 — 100% 문서 근거는 아니다.
- 이미지 크기/종횡비 휴리스틱은 표본 2장으로는 판단 불가하다는 것 자체가 결론이며, 추가 표본 수집은 이번 조사 범위 밖.
