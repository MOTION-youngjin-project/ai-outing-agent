# 토큰 절감 패치 진행 기록

브랜치: `feature/token-usage-optimization`

## 3단계: 모델 사용량 측정

추천(스트리밍 포함), 모델 벤치마크의 모델 콜백에서
서버 콘솔에 `[ai-usage]` JSON을 남긴다. DB 스키마와 이용량 차감 정책은 변경하지 않는다.
프롬프트, 응답 본문, 사용자 식별자, API 키는 기록하지 않는다.

- `requestId`: 한 에이전트 실행의 식별자. 도구 왕복과 모델 폴백도 같은 ID로 집계.
- `operation`: recommendation / benchmark / suggestion.
- `callCount`: 시작된 LangChain 채팅 모델 호출 수. 공급자 HTTP 재시도 횟수와는 다를 수 있다.
- `completedCalls`, `failedCalls`, `pendingCalls`: 콜백으로 확인한 호출 상태.
- `measuredCalls`, `unmeasuredCalls`: 유효한 토큰 메타데이터가 있는/없는 호출 수.
- `inputTokens`, `outputTokens`, `totalTokens`: 메타데이터가 있는 호출만의 누적 합.
- `models`: 호출된 모델 목록.

각 로그는 **누적 스냅샷**이다. 같은 requestId의 로그를 더하지 말고 마지막 것을 사용한다.
타임아웃 뒤 늦게 완료된 호출도 같은 ID의 새 로그에 반영된다.
미측정·진행 중 호출이 있으면 합계를 전체 소비량으로 해석하지 않는다.
입력·출력 합과 totalTokens는 공급자 메타데이터에 따라 다를 수 있다.
이는 채팅 모델 측정이며 PDF 검색의 임베딩 토큰과 공급자 실제 청구액은 포함하지 않는다.
8단계부터 후속 질문 제안은 AI를 호출하지 않는다. 실제 API 측정 결과는 아래 검증 기록에 있다.

검증: `npx tsx --test scripts/ai-usage-check.ts`
외부 API 없이 실제 LangChain 콜백 경로의 일반/스트리밍 호출, 실패, 요청 격리 등을 검증한다.

## 4단계: 저장된 취향 연결

로그인한 사용자 ID로 `preferredTags` 필드만 조회하여 추천 시스템 프롬프트에 전달한다.
현재 저장 가능한 값은 실내·야외·데이트·저비용 4개이며 중복·알 수 없는 값은 제거한다.
태그가 없거나 조회가 실패하면 기존 추천을 계속한다. 사용자 대화나 최근 질문 기록에
취향 문장을 덧붙이지 않고, 취향 처리를 위한 추가 AI 호출도 하지 않는다.

사용자 대화에 환경·동반자·비용 조건이 명시되면 해당 종류의 기본 태그를 생략한다.
예: 실내 선호 + 등산 요청 → 실내 태그 생략, 데이트 선호 + 친구와 여행 → 데이트 생략.
키워드 필터는 모든 자연어 표현을 이해하지 못하므로 프롬프트에도 현재 요청 우선 원칙을 넣는다.
이는 선호 처리이며 이동수단 금지 등 강제 제약 검증을 대신하지 않는다.
저장된 실내와 야외가 모두 선택돼 있으면 환경 선호는 생략한다.

실제 취향 문장을 추가하면 해당 호출의 입력 토큰은 늘 수 있다. 불필요한 되묻기를
줄이기 위한 연결이며 이 단계만으로 토큰 절감이 보장되지는 않는다.
이동수단·고양이 등 자유 취향은 현재 저장 스키마에 없어 이번 단계에서 추가하지 않았다.
검증: `npx tsx --test scripts/recommendation-preferences-check.ts scripts/ai-usage-check.ts`

## 5단계: 동시 중복 요청 차단

`/api/recommend`에서 인증 후 사용자 ID·대화 ID·전체 대화·유효 좌표를 SHA-256 키로 만든다.
같은 키가 진행 중이면 HTTP 409와 `recommendation_in_progress`를 반환한다.
원래 요청은 계속 진행한다. 중복 요청은 결제 가능 여부 확인·자동충전·AI 호출·이용량 차감에
진입하지 않는다. 완료·생성 실패·결제 불가·결제 확인 예외 시 잠금을 해제한다.
연결이 끊겨도 실제 작업이 끝나기 전에는 잠금을 해제하지 않는다.

잠금 자체는 완료 결과 캐시가 아니다. 완료 후 재요청은 아래 6단계 캐시 규칙을 따른다.
서버 프로세스 메모리를 사용하므로 여러 프로세스·서버 간 중복 방지는 보장하지 않는다.
다른 내용의 동시 요청 사이 잔액 경쟁은 이 변경의 범위가 아니다.
진행 중 키 1,000개가 차면 신규 요청에 503을 반환하며, 진행 중 잠금을 시간만으로
삭제해서 중복 실행을 허용하지 않는다.

검증: `node --import tsx --experimental-test-module-mocks --test scripts/recommendation-lock-check.ts`
실제 라우트에 모의 인증·추천·결제를 연결해 중복 시 AI 및 결제 확인 1회,
차감 1회, 실패 후 재요청을 검증했다. 실제 결제·외부 AI는 호출하지 않았다.

## 6단계: 추천 결과 캐시

인증 후, 결제 확인 전에 서버 메모리 캐시를 조회한다. 동일 사용자·대화 ID·전체 대화
(지역/날짜/시간/이동수단 등 입력 포함)·정확한 GPS 좌표·정규화된 저장 태그·한국 날짜가
모두 같을 때만 완료 결과를 재사용한다. 의미가 비슷한 문장을 동일 조건으로 추측하지 않는다.
다른 사용자와 결과를 공유하지 않는다. 취향은 한 번 읽은 스냅샷을 추천에도 그대로 전달한다.

- 유효 시간: 생성 완료 후 5분. 한국 날짜가 바뀌면 재사용하지 않는다.
- 용량: 프로세스당 최대 200개, 결과당 128KiB. 재시작하면 사라진다.
- 적중: 기존 결과·기록 ID를 반환하며 AI·임베딩·결제 확인·추가 차감·새 기록 생성을 건너뛴다.
- 미적중: 기존 생성·차감 흐름. 되묻기, 장소 없는 결과, 코스 저장 실패는 캐시하지 않는다.
- 조회 시 현재 사용자 취향 및 기존 추천 기록의 소유자·만료·존재를 DB로 확인한다.
  DB 확인 실패나 삭제된 기록은 재사용하지 않는다.
- 응답은 기존 NDJSON 형식을 유지하며 `X-Recommendation-Cache: hit/miss`를 추가한다.
- 5분 동안 날씨·운영·교통 정보가 달라질 수 있다. 적중마다 실시간 정보를 다시 조회하지 않는다.
- 전체 대화나 대화 ID가 바뀌면 미적중이므로, 화면에서 후속 질문을 보내는 경우에는
  같은 단어를 입력해도 캐시가 적중하지 않을 수 있다. 다른 코스 요청도 새 입력으로 처리한다.
- 후속 질문 제안 API는 별도 HTTP 호출이지만, 8단계부터 모델은 호출하지 않는다.

검증: `node --import tsx --experimental-test-module-mocks --test scripts/recommendation-cache-check.ts scripts/recommendation-lock-check.ts`
라우트 적중 시 생성/결제 확인/차감 각 1회, 만료·조건 변경·삭제·DB 장애 우회 등을 검증했다.
이 캐시 테스트에서는 실제 Gemini/결제 API를 사용하지 않았다.

## 7단계: 반복 추천 방지

새 생성 시 해당 사용자의 최근 7일·최근 5개 추천에서 최대 20개 장소명을 가져온다.
짧은 제외 목록을 모델에 전달하고, 응답 후에도 이름을 정규화하여 중복을 코드로 제거한다.
현재 응답 안의 동일 장소도 제거한다. 모든 후보가 겹치면 추가 모델 재호출 없이
조건 확대/재방문을 요청하는 안내를 반환하며 장소가 없으므로 차감하지 않는다.
특정 장소를 직접 요청하거나 같은 곳 재방문을 명시하면 허용한다.
"같은 곳 말고"처럼 부정하는 문장은 제외를 유지한다.
동일 요청 캐시 적중은 기존 결과 다시 보기이므로 이 생성 단계를 거치지 않는다.

현재 DB에는 방문 완료·관심 없음 상태가 없어 그 상태를 추측하지 않는다.
이름이 완전히 다른 별칭은 중복으로 인식하지 못할 수 있다.
여러 캐시 코스를 무작위로 섞으면 요청 조건을 위반할 수 있어 이번 구현은
정확히 일치한 결과만 재사용하고 새로운 조건에는 제외 목록으로 새 추천을 만든다.

## 8단계: 입력·호출 절감

- 후속 질문 제안은 로컬 규칙으로 처리한다. 기존 모델 호출은 0회가 된다.
- PDF 선검색에 AI 답변을 제외한 사용자 조건만 전달하고 상위 3개 자료를 사용한다(기존 5개).
- 실제 추천 모델에는 기존 대화를 보존한다. 예산·금지 조건을 임의 요약/삭제하지 않는다.
- 임베딩 질의 캐시와 기존 날씨 선조회는 유지한다.

## 9~10단계: 검증 및 실행 방법

자동 검증:

```powershell
node --import tsx --experimental-test-module-mocks --test scripts/ai-usage-check.ts scripts/recommendation-preferences-check.ts scripts/recommendation-lock-check.ts scripts/recommendation-cache-check.ts scripts/recommendation-diversity-check.ts
npm run lint
npm run build
```

새 검증 17개, 기존 self-check 98개, TypeScript 검사, 전체 lint 및 프로덕션 빌드를 통과했다.
중복 부정 표현 버그는 실패 테스트를 먼저 확인하고 수정 후 통과했다.
외부 DB 없이 빌드할 때는 Prisma 생성용 테스트 DATABASE_URL을 제공했다. DB 변경은 없다.
저장소 PM2 설정은 다중 인스턴스를 지정하지 않는다. 실제 운영 프로세스 상태는 조회하지 않았다.

실제 모델 검증(2026-09-21): 기존 키로 지역을 되묻는 짧은 요청 1회를 보냈다.
gemini-3.5-flash-lite: 모델 호출 1회, 입력 2,524 / 출력 83 / 총 2,607토큰,
미측정 0회. 앱 추천 DB·이용량 차감·실제 결제는 호출하지 않았다.
이는 메타데이터 수집 검증이며 전체 여행 추천의 전후 절감률이 아니다.

명시적으로 실제 모델 측정을 다시 실행할 때:

```powershell
$env:RUN_LIVE_TOKEN_CHECK='1'
# GEMINI_API_KEY를 환경변수로 제공하거나 TOKEN_CHECK_ENV_FILE에 로컬 env 파일 경로 지정
npx tsx scripts/token-usage-live-check.ts
```

검증된 절감 동작: 동일 요청 2회 테스트에서 추천 생성 1회·결제 확인 1회·차감 1회.
적중 요청은 추천 생성 호출 0회. 제안 문구 생성은 항상 모델 호출 0회.
전체 평균 절감률은 운영에서 캐시 적중률 및 requestId별 마지막 토큰 로그를 모아 계산해야 한다.

작업 위치: `D:\motion-token-optimization`. 배포 시 추가 환경변수·DB 마이그레이션은 필요 없다.
기본 캐시 설정은 `src/lib/services/recommendation-cache.ts`의 TTL/용량 상수에 있다.
되돌리려면 이 패치 커밋을 revert한다. 배포·병합은 이번 작업에 포함하지 않는다.
